# Gatekeeper v0.1.0 — Identity & Access Management Foundation

First stable release of the IAM foundation milestone. Java 21, Spring Boot 4.2.0
and the official Authorization Server integrated in Spring Security 7.2.0 form a
modular backend with explicit security boundaries.

- Identity lifecycle, Argon2id credentials and temporary account/source abuse controls.
- PostgreSQL-backed JDBC sessions, fixation rotation, cookie security and CSRF enforcement.
- Server-side roles/permissions, ownership and deny-default authorization.
- RFC 6238 TOTP possession proof, encrypted seeds, replay prevention and single-use recovery codes.
- Hashed expiring password-reset credentials with atomic single consumption and revocation.
- OAuth 2.0 Authorization Code, OpenID Connect discovery/ID tokens/JWKS, mandatory S256 PKCE and exact redirects.
- Short-lived RS256 JWTs, confidential refresh rotation, replay-triggered family revocation and serialized code/refresh exchanges.
- Standard token revocation, credential-version invalidation and append-only persistent security audit.
- PostgreSQL 18.7/Flyway, real Testcontainers/HTTP adversarial tests, Docker clean-start and protected GitHub Actions checks.

Validation: 3 unit plus 16 integration/security/protocol/concurrency tests; zero
failures, errors or skips. G1–G20 cover storage, sessions, authorization, MFA/recovery,
OAuth/OIDC, replay/races, revocation, audit and credential leakage. The resolved
dependency audit checks all 144 Maven coordinates with no advisory suppressions.
Source, history, reports and CI artifacts are checked for credential leakage.

Release preparation changes project version, matching Docker references and release
documentation only; it does not change IAM behavior or dependency versions from the
audited `dev` implementation. CI on the final main SHA gates the annotated `v0.1.0` tag.

## Security / Scope Notes

This is a portfolio/backend IAM foundation; a stable milestone release is not a
production certification, independent pentest or claim of complete security.
TOTP is not phishing-resistant. A real verified recovery/email provider and KMS are
not included; delivery is a local/test fake. Signing-key overlap rotation is documented
but not implemented. External offline JWT consumers observe revocation according to
expiry/skew. Production DB-role separation, automatic audit retention/export and
distributed abuse controls remain operational/roadmap work. Database administrators
can defeat local append-only triggers, and the OAuth JDBC store/backups require
protection because they retain bearer values. In-flight operations may complete after
revocation. See [security model](../security-model.md), [operations](../operations.md)
and [testing](../testing.md) for the precise guarantees and residual risks.
